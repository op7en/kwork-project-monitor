**Goal:** durable single-user monitoring with no repeated automatic project send.
**Architecture:** SQLite tombstones and atomic reservation; Gmail history cursor; deterministic classifier; owner-controlled, memory-only scheduler. Existing MIME, table policy and private notifier remain the boundaries.
**Spec:** owner's Milestone 5 request in this conversation. Baseline a445dca3085baf67c77d1a42c79a56b1cc720db6 verified locally and via GitHub.

## Risk decisions before implementation

1. Five-result search is neither exhaustive nor an incremental cursor. Keep it for the legacy metadata checker; monitoring uses messageAdded history, not timestamp search.
2. Equal timestamps, pagination and delayed arrival cannot be solved by max(timestamp). Store Gmail historyId as a decimal string; collect all bounded pages before body work. Capture an upper history fence before enumeration; only process events through that fence. Advance only after complete processing. Changes arriving later remain for the next pass.
3. More than the bounded page/ID allowance returns overflow before bodies, preserves cursor and pauses automatic monitoring. No silent truncation. Owner may explicitly rebaseline, accepting skipped backlog; no auto full-mailbox sync.
4. Global projectId primary key survives multiple emails and restarts. Message IDs have a separate ledger. Never prune dedup tombstones automatically.
5. Commit message state and all project reservations in one transaction before sends. Crash after reservation loses a card but cannot resend it. On restart reserved becomes delivery_unknown.
6. Existing notifier intentionally hides all send exceptions. All telegram_error outcomes conservatively become delivery_unknown, including definite API rejection; sent requires API success. No automatic resend in either case.
7. Parse/MIME failure is terminal parse_failed for that message, with fixed codes/counts only, no payload saved. No endless body reread. Transient message read failures get at most three attempts over separate passes, never an immediate retry; terminal read_failed after that.
8. First on saves current Gmail historyId only, no history search/body/send. A metadata internalDate activation floor also rejects old imported/backdated mail. First-init boundary deliberately excludes preactivation mail, including delayed preactivation messages.
9. Do not persist destination confirmation or opt-in. Every process begins off; genuine private-owner /monitor on confirms destination and activates it. /start alone cannot enable monitoring. Pending updates are dropped at production startup so a queued old on cannot activate it.
10. Recursive timeout, default six hours, arms only after explicit on and after settled pass. /projects uses the very same monitoring service in production; no parallel legacy sending. off/shutdown prevent further external operations, drain the current request and only then close storage.
11. Match requires supported technology AND a bounded task signal; auxiliary technology also needs a small-scope signal. CMS/complex/mixed/low-evidence signals produce exclude or review. Optional price/customer metrics only raise caution; missing values are not invented. Automatically send match only. Review is counted/stored, not sent. Rules are typed source configuration, not mail commands.
12. PostgreSQL/ORM/service adds unnecessary single-user operational burden. node:sqlite already ships in required Node 24, provides transactions, unique keys and crash recovery. Local disk only, WAL + FULL sync; built-in API is experimental in installed Node 24.1. No npm dependency needed.

Additional risks:
- History cursor can expire (404): pause, never silently full-sync or baseline. Explicit /monitor baseline while off is metadata-only and keeps project tombstones.
- SQLite unavailable/corrupt/schema mismatch: fail closed before Gmail/send, no auto delete/recreate. Losing/restoring an older DB also loses dedup guarantees; preserve backups consistently.
- Different accounts/owners must not reuse the DB silently. Persist a SHA-256 configuration identity binding, no account/credential values.
- Two processes: SQLite session row acquired atomically, bound to local host/PID; second live owner is refused. Dead PID permits restart recovery. Uncertain PID/host and PID reuse fail closed. Only local filesystem supported; no network-mounted DB.
- Send limits: cap cards/pass and parsed projects/pass. Incomplete passes keep cursor; already committed message/project tombstones allow progress next interval without repeated sends.
- Stop during send: in-flight send can finish; result is persisted before draining. Stop before send leaves reserved -> delivery_unknown. No abort interpreted as permission to retry.
- State grows because guarantees need tombstones. Row threshold/page cap pauses safely rather than evicting IDs.
- No exact-once delivery: at-most-one application send attempt while ledger is intact. SDK HTTP retries are a separate transport property (F2). No auto-retry plugin is installed.
- From allowlist is not cryptographic sender authenticity; URL/text validation remains mandatory.
